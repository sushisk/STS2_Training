# docs/ 編集ルール

このディレクトリを編集する前に読む短いガイド。

## ドキュメントの2種類

`docs/` には性質の異なる2種類の文書が混在している。どちらに属するかで従うルールが変わる。

1. **コード解説ドキュメント**(`00_overview.md` 〜 `08_visualizer.md`): `src/sts2_training/` の各モジュールを説明する。下記「文章編集ポリシー」に従う。
2. **wire protocol / paired release 文書**(`STS2_wire_contract_v0.*.md`, `emulate_actions_timeout_semantics_v0.7.md`, `paired_v07_release_assurance.md`, `whole_run_action_id_cutover.md`): STS2_RL と共有するバージョン管理された契約・移行記録。固定フォーマットを強制しない。新規追加時は既存ファイルの書式(バージョン番号の付け方、"paired with sushisk/STS2_RL#N" の明記など)に合わせる。

## 文章編集ポリシー(コード解説ドキュメント)

- **固定フォーマットを厳守する**: `## 0. 文章の目的` / `## 1. 概要` / `## 2. Architecture` / `## 3. API` / `## 4. 使用例` / `## 5. 補足説明` の6見出しを、この順序・この番号で必ず含める。
- **すべての主張は実際のソースを読んで検証する**: 関数シグネチャ、フィールド名、デフォルト値、スキーマ/バージョン番号(例: `ORACLE_RECORD_SCHEMA_VERSION`)は記憶やこれまでのドキュメントの記述を信用せず、該当する `src/sts2_training/` の実ファイルを開いて確認する。`## 4. 使用例` のコードは実際に動く形にする(存在しない引数・インポートパスを書かない)。
- **現在の実装だけを書く**: 将来の拡張予定や未実装の構想を、現在動く契約であるかのように書かない。書く場合は `## 5. 補足説明` に「将来の拡張予定」として明記する。
- **重複させず相互参照する**: ある概念(例: score 用語、DTO契約)を別モジュールの文書で使う場合は、その概念を定義しているファイルへ相対リンク(`[02_decision_core.md](02_decision_core.md)`)で参照する。定義をコピーしない。
- **日本語で書く**。コード識別子はバッククォート、コード片は ``` フェンスで囲む。

## ファイル新規作成ポリシー

- コード解説ドキュメントを追加する場合、`src/sts2_training/` の既存モジュール構成に対応させる。既存ファイルのどれかのスコープに収まるなら新規ファイルを作らず、そのファイルを拡張する。
- 新しいモジュール/サブシステムを追加した場合のみ、次の空き番号で `NN_<topic>.md` を作成し、固定フォーマットに従い、`00_overview.md` の索引テーブルに1行追加する。
- 番号・ファイル名は一度決めたら変更しない(相互リンクが壊れるため)。リネームが必要な場合は全ファイルの参照リンクを一括更新する。

## そのほか注意点

- **マージ前に事実精度レビューを行う**: 記載した API シグネチャ・設定フィールド・使用例を、自分で書いた直後にもう一度実ソースと突き合わせる。今回の全面刷新では、最初の草稿の約半数のファイルに「動かないコード例」「存在しない引数」レベルの誤りがあった。書いた本人による一度の確認では見逃しやすいため、可能なら別の視点(別セッション、別レビュアー)で再確認する。
- **API を変更したら同じ PR でドキュメントも更新する**: ドキュメントとコードの乖離は静かに蓄積する。シグネチャや設定フィールドを変えたら、対応するモジュール文書の `## 3. API` と `## 4. 使用例` を同じ変更でなおす。
- **`00_overview.md` の索引テーブルを常に最新に保つ**: ファイルの追加・削除・大幅なスコープ変更をしたら、この索引も同時に更新する。
